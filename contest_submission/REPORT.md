## 1. 方案总体架构

```
  prompt.txt ─┐
              ├─► 提示词组装 ──► LLM ──► 代码抽取 ──► solution.v
 interface.txt┘        ▲                                  │
                       │                    ┌─────────────┤
                  技能注入 ◄── 触发词匹配 ◄──┤ check_interface  (纯文本，微秒)
                       ▲                    │ lint  xvlog+xelab (秒级)
                       │                    │ synth synth_design (数十秒)
                       └────── 最多 3 轮 ◄───┘
                                                          ▼
                                            solution.v + trace.jsonl
```

### 1.1 设计依据

三个工具按代价从小到大排，`check_interface` 在最前。理由是 RTL 侧端口名或模块名
写错会让详细描述失败，整题落 L0；而这件事纯文本比较即可判定，花一次 `xelab`
去发现它是浪费。第 7 节给了实测的等级分布支撑这个排序。

环内不做 cosim 之类的重验证，因为参考测试台不下发，能做的最强验证就是综合。

## 4. 智能体设计

### 4.1 控制流

见 `agent/main.py::solve_agent`。每轮：组装提示词 → 调模型 → 抽代码 →
`check_interface` → `lint` → `synth`，任一步失败即把压缩后的日志带入下一轮。
上限三轮。

### 4.2 重试与回退策略

每轮从头重新生成，不做局部修补。选择重生成而非修补的理由是实现简单；**这不是一个
经过验证的选择**，见第 7 节。

墙钟预算在轮之间等分，每轮开始前检查剩余时间，不足则直接返回当前最好结果。
赛事方侧超时一定是 L0，自己先停至少还有 L1 的可能。

### 4.3 上下文管理

`tools.py::summarize_log()` 保留含 `ERROR:` / `Synthesis finished` 等关键词的行，
截断到 2 KB。一份综合日志有数千行，整份回灌会吃满上下文并把唯一有用的那一行埋掉。

### 4.4 自我验证

**没有做。** 这是本方案最大的缺口，见第 7.3 节。

## 5. 技能包

### 5.1 技能清单

| 技能名称                         | 解决什么问题                   | 适用条件                                                     |
| -------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| `rtl-module-interface-contract`  | 模块名/端口名/方向/位宽与接口不符 | 日志有 `VRFC 10-3180` / `VRFC 10-2063` / `VRFC 10-4982` |

采用 AMD 官方技能格式，正文英文，可与官方技能混放，见 `skill/README.md`。

### 5.2 提炼过程

该技能针对的是本赛道特有的一个约束：**参考测试台不下发**，它按接口里的声明用
具名端口连接例化被测模块（`.q(q_dut)`），故该声明构成接口契约。端口一旦改名
就是少一个端口，详细描述当场失败。

从早期失败样本中归纳出五类违约（模块名、端口名、方向与位宽、模块头语法、
文件里混入测试台内容），每一类对应一条可机械判定的规则。

### 5.3 有效性验证

在 Vivado 2026.1 / `xczu3eg-sbva484-1-e` 上逐条注入故障实测：

| 注入的故障                         | 工具输出                                                        | 判定等级 |
| ---------------------------------- | --------------------------------------------------------------- | -------: |
| 模块头缺分号                       | `ERROR: [VRFC 10-4982] syntax error near 'always'`               | **L0** |
| 端口 `q` 改名为 `out`              | `ERROR: [VRFC 10-3180] cannot find port 'q' on this module`      | **L0** |
| 模块名写成 `top_module`            | `ERROR: [VRFC 10-2063] Module <TopModule> not found`             | **L0** |
| 接口正确、reset/load 优先级写反    | `Mismatches: 5 in 229 samples`                                   | **L1** |
| 接口与功能均正确、含 `real`        | `ERROR: [Synth 8-6156] failed synthesizing module 'TopModule'`   | **L2** |
| 对照组                             | `Mismatches: 0 in 229 samples` + `Synthesis finished with 0 errors` | **L3** |

三个可直接用于排序修复优先级的结论：

- **接口错一律 L0，功能错还有 L1。** 端口写对比算法写对更值钱，这不是多数人从软件
  带来的直觉。
- **语法错误报的行号是错的。** 分号漏在端口列表末尾，`xvlog` 报在下一行的
  `always` 上。看到一个明明没问题的关键字报语法错，先看它上面一行。
- **接口类错误纯文本可判**，所以 `check_interface` 放在工具链最前，不消耗 Vivado。

*说明：本节数据为本仓库实测。写实证时务必标注工具版本、器件与测量口径。*

## 7. 失败分析

### 7.1 仍然做不出来的题目类型

| 题目类型             | 卡在哪一级 | 原因判断                                             |
| -------------------- | ---------- | ---------------------------------------------------- |
| 多状态 FSM           | L1         | 状态编码与转移能写对，但复位后的初始状态经常错一拍   |
| 时序语义敏感的题目   | L1         | 同步复位写成异步、阻塞与非阻塞混用，逐拍比对失败     |
| 题面含波形或状态图   | L1/L0      | 纯文本题面里图形信息丢失，模型推不出转移表           |

### 7.2 尝试过但无效的改进

| 尝试的做法         | 预期效果       | 实际结果       | 为什么无效                       |
| ------------------ | -------------- | -------------- | -------------------------------- |
| 把轮数从 3 提到 6  | 通过率上升     | 基本持平，墙钟翻倍 | 失败集中在功能错误，而环内检查不到功能，多给轮次也没有新信息 |

### 7.3 方案的边界

最先崩掉的是**功能正确性**这一维。整条链路里没有任何环节能判断算得对不对，因此
L1 → L2 这一步（系数从 0.2 到 0.7，全表最大的一跳）完全靠模型一次写对。

换一个更弱的模型，崩的顺序会变成：先是代码抽取失败（不按格式输出），再是接口不符，
最后方为时序语义。可见在小模型上，格式与接口约束带来的收益高于设计能力，而这两项
恰好都是确定性检查能覆盖的。

## 8. 复现说明

### 8.1 构建

由赛事方在平台内部按 `Dockerfile` 重建（仅退路方式需要）：

```bash
docker build -t example-agent .
```

### 8.2 启动推理服务

```bash
MODEL=/models/Qwen3-8B ./serve/vllm.sh &
export LLM_BACKEND=openai LLM_BASE_URL=http://localhost:8000/v1
export LLM_MODEL=Qwen3-8B LLM_API_KEY=dummy
```

### 8.3 单题运行

```bash
./run.sh <input_dir> <output_dir>
```

### 8.4 基线运行

```bash
./run_baseline.sh <input_dir> <output_dir>
```

### 8.5 已知的环境依赖

- 权重须在断网前落到本地盘，`huggingface-cli download` 在沙箱中会失败
- `AGENT_TMP` 必须指向本地目录（实例上用 `/var/tmp`），不能是 `/workspace`。指向 NFS 时综合会慢一个数量级
- `xvlog` / `xelab` / `xsim` / `vivado` 四个命令须在 `PATH` 上
